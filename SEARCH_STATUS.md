## Pinned model

Firmware boundary:

- COLDCARD firmware tag `2023-06-26T1241-v4.1.9` (commit shown by that tag: `bc511ee`)
- libngu submodule commit pinned by that firmware tree: `356b9137`
- main paths: `shared/seed.py`, `shared/nvstore.py`, `shared/mempad.py`,
  `external/libngu/ngu/random.c`, MicroPython `ports/stm32/rng.c`

Initial chip state:

```text
pad = UID_low32 XOR SysTick->VAL
n   = RTC->TR
d   = RTC->SSR
dat = 0
```

For the clean cold-boot hypothesis, `RTC_TR=RTC_SSR=0`. Every UID/timer pair
then maps into one 32-bit `pad`; enumerating `pad=[0,2^32)` covers every such
preimage without knowing a device UID.

## Do we need the device UID?

**No for completeness; yes for speed.** The firmware reads one 32-bit word from
the STM32 unique-ID address and XORs it with `SysTick->VAL`:

```text
pad = UID32 XOR SysTick->VAL
```

Without `UID32`, a full `2^32` pad pass covers every possible UID/timer
preimage. With the actual device's `UID32`, the Mk3's 80 MHz clock and 1 kHz
SysTick constrain `SysTick->VAL` to approximately 80,000 values (`0..79999`).
The pad set becomes `{UID32 XOR t | 0 <= t < 80000}`: approximately **53,687×
fewer initial candidates** than `2^32`.

UID knowledge does not identify the RTC state, P/Q call history, setup path,
address derivation, BIP39 passphrase, or dice use. It shrinks one search
dimension; it does not determine the seed. The current CUDA scanner accepts
contiguous pad intervals, so the highest-value UID-aware code change is an
explicit pad-list input plus a full-pass equivalence test.

First fresh-wallet flow:

```text
shuffle(32 empty nvstore slots)                         31 chip draws
48 × random.bytes(256)                                  3072 chip draws
P pre-Terms keypad scan sessions × shuffle(4)           3P chip draws
first Terms/settings save × shuffle(32)                 31 chip draws
Q post-Terms keypad scan sessions × shuffle(4)          3Q chip draws
random.bytes(32)                                        candidate seed bytes
```

Therefore the chip offset before seed generation is:

```text
chip_skip = 3134 + 3 × (P + Q)
```

The mixer offset is **not** a fixed formula. Libngu `_rand_below()` consumes one
chip and one mixer word on its first attempt; rejection retries consume
mixer-only words. Correct first-boot mode therefore replays the source flow per
candidate and obtains a pad-dependent `mixer_skip`.

## What a no-hit actually means

If one pass exhausts, the defensible statement is:

> No address in the stated target hash matched any BIP84 account-0 external
> index in the stated index range for `pad=[0,2^32)`, `RTC=0/0`, `P=2`, the
> stated Q history, and the source-faithful fresh-erased-device call flow.

It does **not** establish any of the following:

- that the firmware defect is harmless;
- that the incident addresses were not generated by affected firmware;
- that another RTC/call history, derivation path, BIP39 passphrase, or dice input
  would not match;
- that every address in the incident list is a victim address or even a Mk2/Mk3
  address;
- that the public thefts used this exact exploit rather than another route.

## If the funded-budget plan finishes with no hit

Do not repeat the same pad ranges. The next work should reduce uncertainty in
this order:

1. **Derivation coverage:** add an index start, BIP84 change chain/account
   ranges, then BIP44/BIP49 for the 23 legacy targets. Reclassify each target by
   script type and transaction role before spending.
2. **Physical history coverage:** enumerate contiguous plausible P/Q scan
   sessions (fast keypresses can merge sessions), optional USB/settings saves,
   and the valid-settings baselines 30 and 0. Simulate source-reachable histories
   rather than arbitrary Cartesian skip pairs.
3. **Empirical device trace:** instrument an affected Mk3 to measure first RNG
   state, retained/warm RTC behavior, keypad session timing, rejection counts,
   and optional setup flows. Hardware measurements should choose the next GPU
   hypotheses.
4. **Corpus provenance:** independently classify which public addresses are
   attributable to affected Mk2/Mk3 seeds, which may use passphrases/dice, and
   which are attacker/change/destination addresses. An unclassified on-chain
   list is not proof that every target must be recoverable.
5. **Alternative truth test:** preserve the possibility that the public drain
   correlation is incomplete or that exploitation used a different weakness.
   Treat a real address match plus an independently verified inert BIP322 proof
   as the threshold for claiming this exact path caused a real compromise.

A no-hit narrows hypotheses. It is not permission to overstate either safety or
exploitability.
